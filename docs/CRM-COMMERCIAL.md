# Native commercial CRM in the existing Node client

`Factuarea.crm` composes the same HTTP client and per-client authentication as the other resources. Entity inputs use `crmUuid()` (UUID v7), user references use `crmUserUuid()`, and Opportunity amounts use `crmDecimal()` (decimal(20,4) input grid, never a JS number). Lead estimated value uses `crmEstimatedValueDecimal()` and its distinct native decimal-string grid. CAS versions reject integers above JavaScript's safe range. Optional request fields distinguish absence from explicit null; explicit undefined, unknown keys, and future write enums fail before HTTP. Nullable masked read fields remain null. Known read enums fail closed if the server adds a value; additional JSON response fields are retained and frozen. Governance JSON subobjects are typed as JSON, not as an authorization grant.

Prepare one of `prepareLeadCreate`, `prepareOpportunityCreate`, `prepareOpportunityStage`, or `prepareActivityCreate` with a stable raw key. Persist its `firstBody`, `idempotencyKey`, operation and optional stage target privately before the matching write. Preparation freezes the first JSON wire; later input mutation does not alter it. A prepared intent belongs to its client and permits one POST attempt. Reuse after dispatch and cross-client dispatch are rejected. The server derives current Company, actor, sandbox, connection, fine scopes and C7. The SDK supplies no synthetic lineage or authority.

Native routes are `/v1/crm/leads`, `/v1/crm/opportunity`, `/v1/crm/opportunity/{opportunity}/stage` and `/v1/crm/crmactivity`. Exact public operationId publication and generated-resource parity remain dependent on Root's final booted OpenAPI. This handwritten native extension does not regenerate the older bundled specification. Lead list uses the actual nested `data.data`, `next_cursor` and `has_more`, with the `cursor` query parameter. `iterateLeads` captures query and client immediately, rechecks current bearer on every page, retains AbortSignal, rejects repeated cursors and has an explicit page ceiling.

All commercial writes send once, for genuine OAuth and API keys. No 401 refresh, redirect, 429, timeout or 5xx turns into write retry. 422, 409, 401/403 and 429 use the existing `ValidationError.fields`, `ConflictError`, `AuthenticationError` and `RateLimitError.retryAfter`. Native unconfirmed receipts, transport/body timeout, cancellation after dispatch, 5xx and invalid success representations raise `CrmCommercialWriteUnconfirmedError` with the original intent. Recover explicitly through `crmOriginals.recover(intent)`; this GET asks the server to prove current native lineage or actual API-key singleton. The key and first body remain unchanged. A confirmed Lead can contain only its identity receipt; a confirmed Activity can contain `activity: null` without losing its confirmed activity/effect IDs. Current Opportunity GET can return null.

The server example `examples/crm-website-server.ts` reads `FACTUAREA_OAUTH_BEARER` or `FACTUAREA_API_KEY` only on the server and requires an atomic durable application reservation. Duplicate submissions use original GET recovery, changed bodies return 409 and uncertain results return 202. Install the handler only in server code and apply the website's own input, abuse and CSRF controls. No secret, retained body, private provider response or credential enters its browser response. `examples/crm-commercial-journey.ts` uses native confirmed IDs to connect Lead → Opportunity → Activity and stops immediately on an uncertain or rejected write. It queries the current Opportunity without asserting that a private Activity projection is visible.

Directed offline tests use fake fetch only. Publication, live grants, backend runtime, final OpenAPI generation and full inventory conformance are separate evidence; this source does not claim them.
